# Adversarial Review (r2) — gitlab-backup Architecture Spine

- **Target:** `ARCHITECTURE-SPINE.md` (2026-11-03, 1-blob+1-hash re-derivation)
- **Altitude:** feature — single bash script, six stage functions (`CAPTURE BUNDLE ENCRYPT HASH SHIP PRUNE`) + BATS test file
- **Method:** for each hole, two builds are exhibited that both obey every AD and convention to the letter yet are mutually incompatible (different on-disk artifacts, different failure attribution, or one ships what the other refuses to publish).
- **Verdict: REJECT — do not build.** At least nine holes admit compliant-but-incompatible pairs; three of them (H1, H2, H4) silently produce unshippable or corrupt-looking sets, and two (H4-remote, H6) admit data-loss behaviors. Close the holes with the suggested AD tightenings, then re-review.

Scope note: this review attacks only the spine. It does not re-litigate settled SPEC decisions (newest-2, exit-1, single script).

---

## H1 — `SHA256SUMS` filename field is unpinned (hash-format seam)

**What the spine says:** AD-5 + Conventions require "`sha256sum -c` format", "one line", "single hash over sealed blob". Nothing pins the filename field (bare basename vs path), the separator (text `␣␣` vs binary `␣*`), or the generating cwd.

**Build A (bare basename, relocatable):** `HASH` runs `(cd staging && sha256sum set.tar.age > SHA256SUMS)`, producing `<hex>␣␣set.tar.age`. The manifest verifies anywhere the two files are co-located: local staging, local published `<ts>/`, remote staging, remote published.

**Build B (absolute path, staging-locked):** `HASH` runs `sha256sum "$STAGING/set.tar.age" > "$STAGING/SHA256SUMS"`, producing `<hex>␣␣/…/.staging-<ts>/set.tar.age`. This is genuine `sha256sum` output format; `sha256sum -c` passes inside staging exactly as AD-2 demands. It then fails in the published dir (path no longer exists) and on the NAS (path never existed), so `SHIP`'s remote re-verify fails every run — a pipeline that always obeys AD-2 locally and always dies at `SHIP`.

Both builds satisfy AD-1/AD-2/AD-5 to the letter ("`sha256sum -c` format", "passes inside staging"). A passes end-to-end; B is a compliant brick. A third axis: `sha256sum -b` emits `<hex>␣*set.tar.age` — also `-c`-compatible, also letter-compliant, and a byte-different manifest that strict string-comparing tests or consumers would reject.

**Suggested AD fix (tighten AD-5 + Naming convention):** pin the exact bytes — `SHA256SUMS` is one line, `<64 lowercase hex>␣␣set.tar.age\n` (bare basename, two spaces, text mode, trailing newline), generated by running `sha256sum` with cwd inside the set dir on the bare filename. Add a negative: no directory components, no `*` marker, no second line. Add a cross-stage verification rule: the same file must pass `sha256sum -c` in local staging, local published, and remote staging without modification (this is the test that kills Build B).

## H2 — Wipe set + publish gate disagree (who wipes what; exactly-two vs presence)

**What the spine says:** AD-1/AD-3/AD-4 say `ENCRYPT` wipes "the plaintexts" via `rm` after `age` exits 0. AD-2 says a set is half-built when staging holds "anything other than exactly its two shippable members", but its publish rule says "only when both members are present AND `sha256sum -c SHA256SUMS` passes" — presence, not absence-of-extras. Nothing enumerates the wipe set (native tarball? `set.tar`? staged config copy? compose copy?) or says what wipe failure does.

**Build A (wipe-all + count-gate):** `ENCRYPT` removes native tarball, `set.tar`, and any staged config/compose copies, and fails the stage if any `rm` fails; `HASH` asserts the staging entry count is exactly 2 (`.age` + `SHA256SUMS`) before the `mv`. A wipe failure aborts at `ENCRYPT`; nothing extra is ever published.

**Build B (wipe-set.tar-only + presence-gate):** `ENCRYPT` removes only `set.tar` (its own input; "the plaintexts" = what this stage consumed), ignoring `rm` exit status; `HASH` checks `-f set.tar.age`, `-f SHA256SUMS`, and `-c` passes, then publishes. Leftover native tarball and staged copies ride the `mv` into the published `<ts>/` — a published set containing plaintext beside the sealed blob, in direct violation of AD-4's intent while satisfying every AD sentence: `ENCRYPT` did "`rm` the plaintexts after age exits 0", both members were present, `-c` passed.

The hole has a second jaw: whether `BUNDLE` stages copies at all (see H3). If `BUNDLE` tars live paths directly, Build B's wipe set happens to be sufficient; if `BUNDLE` stages copies first, Build B leaks. So `ENCRYPT`'s correct wipe set depends on an unspecified `BUNDLE` implementation choice — a cross-stage contract hole, not a single-stage bug.

**Suggested AD fix (tighten AD-1/AD-2/AD-3):** (a) enumerate the wipe set by stage output: `ENCRYPT` deletes exactly `{native tarball as named in H5 fix, set.tar}` plus any files `BUNDLE` staged (pin whether `BUNDLE` stages copies — recommend: no staging copies; tar reads live config/compose directly, native tarball is the only staged input); (b) make wipe failure an `ENCRYPT` failure (check every `rm`, fail closed); (c) rewrite AD-2's publish gate as presence-plus-absence: exactly two directory entries, named exactly `set.tar.age` and `SHA256SUMS`, plus `-c` passes. Any third entry aborts with `FAIL:HASH`, never publishes.

## H3 — `BUNDLE` archive layout, `cmp` target, and the `cmp`-vs-one-tool contradiction

**What the spine says:** AD-1: "`BUNDLE` tars the native tarball + whole config volume + compose copy (byte-identical to source, checked with `cmp`) into `set.tar`". AD-3: one tool per stage — `tar` (bundle). `cmp` appears in AD-1 but in no AD-3 tool list.

**Contradiction first — Build A vs Build B on `cmp`:** Build A runs `tar` + `cmp` in `BUNDLE` (reads `cmp` as validation, akin to bash sequencing, hence allowed). Build B runs `tar` only and skips the check (reads AD-3's "one tool per stage" as exhaustive, hence `cmp` forbidden). Both cite a real AD sentence; A fails closed on a compose file that changed mid-run, B silently bundles the drifted bytes. The spine both mandates and forbids the same invocation.

**Layout hole — Build C vs Build D (both `tar`-only, both "tars X+Y+Z into set.tar"):** Build C archives relative members (`native.tar`, `etc/gitlab/…`, `compose.yml` via `-C` flags). Build D archives the staging path itself (members `.staging-<ts>/native.tar`, absolute `/etc/gitlab/…`). Both satisfy AD-1's sentence; they produce mutually unrestorable `set.tar` files, and the consumer contract (owned elsewhere) can match at most one. Companion under-specifications riding the same sentence: compression (`tar -czf` still named `set.tar` is letter-compliant and restore-breaking), permission/ownership flags, and what "byte-identical to source, checked with `cmp`" compares against what and when (copy-vs-live before tar? extract-and-compare after tar, with a TOCTOU window?).

**Suggested AD fix (tighten AD-1/AD-3):** (a) resolve the tool contradiction explicitly: allow `cmp` (and only `cmp`) as a validation adjunct in `BUNDLE`, or move byte-identity into bash/`cmp` preamble language in AD-3 — pick one sentence both builds must satisfy; (b) pin `set.tar` member paths exactly (recommend flat, relative: `<native-name>`, `gitlab-config/…`, `compose.yml` or equivalent, with the exact prefixes stated), forbid compression and absolute members, pin `tar` flags (e.g. `--numeric-owner --sort-name` or explicitly "system defaults"); (c) pin the `cmp` protocol: copy compose (and config, if staged) into staging, `cmp` copy-vs-live before tarring, tar the staged copies, `FAIL:BUNDLE` on mismatch.

## H4 — `SHIP` rsync shape, remote cwd, and the nesting `mv`

**What the spine says:** AD-5: "`SHIP` rsyncs the published set to `<nas>/.staging-<ts>/` (remote layout mirrors local exactly), re-verifies there over ssh (`sha256sum -c`: presence first, then hash-match), and only then renames remotely to `<nas>/<ts>/`."

**Build A (contents-mirror):** `rsync -a published/<ts>/ nas:.staging-<ts>/`, then `ssh nas "cd <nas>/.staging-<ts> && sha256sum -c SHA256SUMS"`, then `ssh nas "mv <nas>/.staging-<ts> <nas>/<ts>"`. Remote published set is `<nas>/<ts>/{set.tar.age,SHA256SUMS}`.

**Build B (dir-mirror):** `rsync -a published/<ts> nas:.staging-<ts>` (no trailing slashes), then verifies in `.staging-<ts>/<ts>/`, then renames. Remote published set is `<nas>/<ts>/<ts>/{…}` — nested garbage every consumer chokes on. Build B's author correctly notes the spine never mentions a trailing slash, never states the remote cwd for `-c`, and "mirrors local exactly" is satisfied under dir semantics (the dir was mirrored, exactly).

**The `mv`-onto-existing jaw:** AD-2's "publish aborts if `<ts>/` already exists" is stated for the local publish. No sentence extends it to the remote rename. Build A checks remote existence and aborts; Build B runs the remote `mv` unconditionally — and `mv a b` when `b` exists nests `a` inside `b`, so a re-shipped timestamp silently becomes `<nas>/<ts>/.staging-<ts>/` instead of failing. Both are letter-compliant; one corrupts the NAS layout.

**"Presence first, then hash-match" jaw:** Build A implements two remote steps (`test -f` both members, then `sha256sum -c`) with distinct `FAIL:SHIP` details; Build B runs one `sha256sum -c` and parses stderr. Same stdout-grammar AD, different `FAIL:SHIP` detail strings and different ssh-call counts (observable to tests counting invocations).

**Suggested AD fix (tighten AD-5 + AD-2):** (a) pin rsync source/dest spellings including trailing slashes and flags; (b) pin the remote verify cwd and exact command(s), and define "presence first" operationally (which files, which command, which failure detail); (c) extend the exists-abort to the remote rename ("remote publish aborts if `<nas>/<ts>/` exists; the remote `mv` never runs onto an existing path"); (d) state remote paths as absolute (`<nas>/<ts>`, not relative `mv` operands).

## H5 — Staging lifecycle and the native-tarball filename (no stage owns the contract)

**What the spine says:** AD-1: "A stage reads only artifacts prior stages left in the set dir." AD-2 names staging `.staging-<ts>/` and its final two members. No AD says which stage creates staging, where `CAPTURE` writes, under what filename, or how `BUNDLE` finds the native tarball (`gitlab-backup create` generates server-side timestamped names like `…_gitlab_backup.tar`).

**Build A (staging-native + pinned glob):** preamble/`CONFIG` creates `.staging-<ts>/`; `CAPTURE` deposits exactly one `*_gitlab_backup.tar` there; `BUNDLE` globs `*_gitlab_backup.tar`, requires exactly one match, tars it.

**Build B (outside-staging + newest-wins):** `CAPTURE` leaves the tarball wherever the container volume lands (outside staging); `BUNDLE` picks the newest `*.tar` under a source dir. Both claim AD-1 compliance ("reads artifacts prior stages left" — B reads "the set dir" as the source/volume dir, since no sentence says `CAPTURE` writes to staging). Under a stale file from a `kill -9`'d run (trap never fired), A fails closed (two matches) while B bundles yesterday's tarball as today's set — silent wrong-data success.

Even within staging-native builds, the handoff filename is unpinned: A expects `*_gitlab_backup.tar`, A′ expects a normalized `native.tar` that `CAPTURE` renames into place. A `BUNDLE` written for one fails on the other's `CAPTURE` output despite both stages being "compliant". Related: AD-2's "half-built when staging holds anything other than exactly its two shippable members" read literally brands every in-progress staging (native tarball present, `.age` absent) as half-built — the intended reading is "at the publish gate", but the sentence states an invariant, so a strict Build C aborts `CAPTURE` for violating AD-2.

**Suggested AD fix (new sub-rule under AD-1/AD-2, the inter-stage contract table):** add a per-handoff table — creator of `.staging-<ts>/` (recommend: run preamble before `CAPTURE`, so a same-second re-run fails fast instead of after a 50 GB capture), `CAPTURE` output path + filename rule (recommend: normalize to a pinned name, e.g. `native.tar`, inside staging), `BUNDLE` input selector (exact glob or pinned name + exactly-one enforcement), `ENCRYPT` input (`set.tar` in staging), `HASH` input (`.age` in staging). Restrict AD-2's exactly-two invariant to the publish gate ("at publish time") so in-progress staging is legal by construction.

## H6 — `PRUNE` scope, `RETENTION_COUNT` vs hardcoded 2, and the victim filter

**What the spine says:** AD-8: "keep the newest 2 set dirs by dirname sort (never mtime) and `rm -rf` whole losers only … Prune never runs unless the current set shipped and verified." AD-6 registers `RETENTION_COUNT` as a canonical variable resolving env > file > default. Deferred work says NAS retention is operator-enforced, not code.

**Three independent pairs:**

(a) **Scope — Build A (local-only) vs Build B (local+remote):** AD-8 never says "local". A prunes `<backups>/` only; B also prunes `<nas>/` over ssh ("set dirs" unqualified). B deletes NAS history the Deferred section assigns to operators — catastrophic, letter-compliant.

(b) **Count — Build A (honor `RETENTION_COUNT`, default 2) vs Build B (always 2):** AD-8 hardcodes 2 ("settles the brief's 2–3 at 2"); AD-6 says retention count resolves via env/file/default. With `RETENTION_COUNT=5`, A keeps 5 and B keeps 2. Each cites its AD; the spine contains both sentences with no precedence rule between them.

(c) **Victim filter — Build A (pattern-filtered) vs Build B (bare sort):** "newest 2 set dirs by dirname sort" — A filters to `^[0-9]{8}-[0-9]{6}$` before sorting; B sorts everything (`ls | sort | head -n -2 | xargs rm -rf`), which, on a host with a stale `.staging-<ts>/` (kill −9) or when `.lock` sorts into the victim window, `rm -rf`s non-set state — including the lock file the run may hold. Both "keep the newest 2 by dirname sort".

**Suggested AD fix (tighten AD-8):** (a) "local `<backups>/` only; `PRUNE` never touches the NAS" (one sentence kills the catastrophic reading); (b) reconcile count: either `RETENTION_COUNT` default 2 honored (recommend — else remove it from the AD-6 registry and say why) with "keep newest `$RETENTION_COUNT`"; (c) pin the victim selector: only entries matching the `<ts>` pattern participate; staging dot-dirs and `.lock` are never victims; (d) pin the "shipped and verified" gate signal (recommend: `SHIP` returned 0 this run — no remote re-probe, which races operator-side deletes).

## H7 — `LOCK` vs `CONFIG` ordering, `LOCK` grammar, and `ts=-` attribution

**What the spine says:** AD-7: "Single-flight via `flock` on `<backups>/.lock`; a second concurrent run exits immediately without waiting. Fixed output grammar (stage vocabulary: `CONFIG CAPTURE BUNDLE ENCRYPT HASH SHIP PRUNE LOCK`): `START <STAGE> ts=<ts>` and `DONE …` to stdout; `FAIL:<STAGE>:ts=<ts>:<detail>` to stderr, exit 1 — `ts=-` when the run dies before its timestamp exists (`CONFIG`, `LOCK`)." AD-1 lists exactly six stages — `LOCK` is not among them. AD-2: "`<ts>` is computed once at run start."

**Build A (`LOCK`-as-stage, lock-first):** lock acquisition emits `START LOCK` / `DONE LOCK` (it is in the stage vocabulary, and every stage presumably logs); config validates after the lock; `<ts>` is computed after `CONFIG`, so `FAIL:CONFIG` always carries `ts=-`.

**Build B (lock-as-preamble, config-first):** the lock is a wrapper, not a stage (AD-1's six are exhaustive), so contention emits only `FAIL:LOCK:ts=-:…` with no `START`; `<ts>` is computed "at run start", i.e. before `CONFIG`, so `FAIL:CONFIG` carries a real `ts`.

Both are defensible readings; they emit different stdout for the same events (extra `START/DONE LOCK` lines vs none) and different `FAIL:CONFIG` lines (`ts=-` vs `ts=<real>`) — any scheduler parser or BATS grammar test written against one fails on the other. Deeper: the lock path `<backups>/.lock` depends on `BACKUP_DIR`, which AD-6 resolves through env/file/defaults and validates in `CONFIG` — so lock-first (A) locks a path it hasn't validated yet (wrong dir if config overrides it), while config-first (B) validates without holding the lock (two concurrent runs can both pass validation, then one dies at lock — after both computed the same `<ts>`, wasting a capture). The spine orders neither.

**Suggested AD fix (tighten AD-7 + AD-6):** (a) state whether `LOCK` emits `START`/`DONE` (recommend: no — contention emits exactly one `FAIL:LOCK:ts=-:<detail>` line to stderr, exit 1, no stdout); (b) pin the order: resolve+validate config → compute `<ts>` → acquire lock → `mkdir` staging (fail-fast on same-second `<ts>/` collision here, not after capture — closes the H5 same-second waste variant); (c) pin `ts=-` to "before `<ts>` assignment" (lock contention and pre-assignment config errors) and require real `ts` after, so attribution is deterministic.

## H8 — `age` key via env-var vs file (AD-4 vs AD-6 contradiction) + recipient shape

**What the spine says:** AD-4: "The public key arrives out-of-band (env var or file path), never hardcoded." AD-6 registry: `AGE_PUBKEY_FILE` — and only that; "no epic invents a variable that bypasses" the registry.

**Build A (file-only):** supports `AGE_PUBKEY_FILE` exclusively; an operator following AD-4's "env var" half has nowhere to put the key. The build cites AD-6's closed registry.

**Build B (both):** also honors an invented `AGE_PUBKEY` env var. It satisfies AD-4's letter and violates AD-6's ("no variable bypasses the registry") — complying with one AD requires breaking the other. The spine is not just under-specified here; it is inconsistent.

**Recipient-shape jaw (both file-based, both "exactly one `age` invocation … against the NAS public key"):** Build C passes `age -R "$AGE_PUBKEY_FILE"` (whole file: all recipients, comments tolerated); Build D passes `age -r "$(head -1 …)"` (first line only). Given a key file with trailing comments/whitespace or (worse) two pasted keys, C encrypts to a different recipient set than D — one of them potentially unsealable by the NAS keyholder or sealable by a stranger. Armor (`-a` vs binary), recipient-flag spelling, and empty/malformed-file behavior are likewise unpinned.

**Suggested AD fix (tighten AD-4 + AD-6):** (a) resolve the contradiction: either register `AGE_PUBKEY` (value, not path — and reconcile with "holds no secrets (key paths, never key material)": a public key is not secret, say so) with file-wins-or-env-wins precedence, or strike "(env var or …)" from AD-4 so file-path is the only shape; (b) pin the `age` invocation (`age -R "$AGE_PUBKEY_FILE" -o set.tar.age set.tar`, binary, no armor), pin key-file format (single `age1…` line; anything else is `FAIL:CONFIG` at up-front validation, including empty file and multi-recipient file).

## H9 — Script↔test interface: function names, signatures, and stubbability

**What the spine says:** Conventions: "One named function per stage." Source tree: `gitlab-backup.sh` + `tests/*.bats` ("per-stage + induced-failure tests"). AD-6: "No host, path, or key literal outside the defaults block." Stack: age is a "vendored static binary" at `vendor/age`.

**Build A (`stage_<lower>` + PATH tools):** functions `stage_capture … stage_prune`, tools resolved via `PATH`, tests stub `docker`/`age`/`rsync`/`ssh` with fakes on `PATH`.

**Build B (`STAGE` + vendored path):** functions `CAPTURE … PRUNE`, `age` invoked at the hardcoded relative path `vendor/age` (Stack says vendored; AD-6's no-literal rule arguably exempts the repo-relative vendor path — or arguably forbids it, since no `AGE_BIN` variable is registered).

A test file written against A's names cannot even call B's stages — "one named function per stage" is satisfied by both and interoperable between neither. Signatures are likewise free: positional `<ts>` arg vs global `$TS` vs recompute-from-`date`; return-by-exit-code vs echo-path. And stubbability cuts both ways: if the script hardcodes `vendor/age`, hermetic BATS tests cannot fake encryption failures (CAP-7 induced-failure tests need them); if it uses `PATH` age, the air-gap story ("vendored static binary") is unenforced and a test-box `age` can silently differ from the pinned 1.3.2.

**Suggested AD fix (new convention or AD-3 sub-rule, the unit contract):** pin the six function names and their signatures (recommend: lowercase `capture`, `bundle`, … taking `<ts>` as `$1`, operating on globals set by config, signaling by exit code + `FAIL:` lines only); state the tool-resolution rule per tool (recommend: `age` via `$AGE_BIN` defaulting to `$SCRIPT_DIR/vendor/age`, registered in AD-6 so tests can override; container/ssh tools via `PATH`); require that every external tool be overridable for tests without editing the script.

## Weaker seams (noted, not full holes)

- **W1 — `CONFIG` validation depth vs one-tool-per-stage.** "Everything is validated up front" (AD-6) invites `ssh`/container/docker probes inside `CONFIG`, whose tools belong to `SHIP`/`CAPTURE` under AD-3's "one tool per stage". A cheap-validate build surfaces bad `NAS_HOST` as `FAIL:SHIP` after 50 GB; a deep-validate build surfaces it as `FAIL:CONFIG`. Pin the validation list (recommend: vars non-empty, files exist/readable, `BACKUP_DIR` writable, `age` key format, container + compose present; no network probes) and state which tools `CONFIG` may use.
- **W2 — `VERBOSE=1` stdout purity.** AD-7 puts `START`/`DONE` on stdout; "VERBOSE=1 gates tool output" doesn't say where tool output goes when ungated. Pin: tool output always to stderr (or `/dev/null` unless `VERBOSE=1`); stdout carries only the grammar lines.
- **W3 — Local pre-ship re-verify.** AD-5 "SHIP only reads and verifies it" suggests a local `sha256sum -c` before rsync; AD-3 assigns `sha256sum` to `HASH`. State whether `SHIP` re-runs `-c` locally (recommend: yes — cheap, closes the publish→ship mutation window — and clarify AD-3 means one tool per *effect*, not exclusive ownership).
- **W4 — Trap semantics.** "Removes local and remote staging (and only staging on each side) on failure" — pin trap type (`ERR` + `EXIT`-on-nonzero), what happens when the remote cleanup `ssh` itself fails (`|| true`, never masks the original `FAIL`), and that a `PRUNE`-failure trap must not touch published sets.
- **W5 — `date -u` spelling.** "Timestamps UTC only" is satisfied by `date +%…` only when `TZ` cooperates. Pin `date -u +%Y%m%d-%H%M%S` literally.

- **H3, H5, H7, H9:** must-fix before per-stage parallel build (cross-unit contract gaps; two authors will diverge).
- **W1–W5:** fix in the same pass; each is one sentence.
